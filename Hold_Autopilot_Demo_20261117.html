The problem

Orders stop on address holds

Fusion rejects the customer address (city / postal not matching Fusion geography, HZ-120485) → GCP puts the order on CUD-604 / CUD-601.

Every hold is manual work

Assign → open Geovalidation Master → validate & correct → wait for Fusion → GCP refresh → comment → release. ~10-15 min per order plus waiting.

Holds pile up

Nights, weekends and busy days: orders wait until someone picks them up.

Same checks every time

Most fixes are the same pattern: Fusion spelling of a city, the right city for a postal code, a county, a postal format.

Release

Geovalidation confirms a fix (01 Full / 00 No Changes) or the hold is stale → correct, refresh GCP, comment exactly what changed, release.

Fusion Action

Postal not in Fusion geography, Fusion error (e.g. ZX-885013) or Fusion IDs stuck → assign "Fusion Action" with an explanatory comment.

Leave

Tax (CUD-511), IT, other non-address holds, unclear fixes, orders someone else already commented on → untouched for the right team.

Faster - parallel processing

Time to work 10 orders:

Before - one at a time: ~51 min
Now - 4 in parallel: ~15 min

4× throughput

4 orders analysed and worked at the same time; orders on the same site stay in sequence.

No wasted waits

Retries wait 4 min, not 12. Orders stuck in Fusion go to Fusion Action after ~25 min instead of 1.5 h.

Quiet cycles ~8 s

No 5-minute run is skipped any more.

Safety built in

Never takes someone else's order

Only unassigned holds; steps aside if a teammate assigns or comments first.

Only confirmed corrections

Applies a fix only when Geovalidation Master validates it (01 Full / 00 No Changes Needed).

Full audit trail

Every action commented in Holds Manager; every decision logged; daily HTML report by email.

Never changes customer status

No site / party deactivation, no order cancel. Repush SQL is logged only, never executed.

No passwords in files

Login read from HashiCorp Vault; if missing, the job writes nothing and logs BLOCKED.

One write at a time

Holds Manager writes serialised; after every release it re-checks ON_HOLD = N.

Always using the latest data

Every morning

Checks SharePoint (ProjectMaverick55 → Geovalidation Master) and installs new updates.zip / extracts.zip with the tool's own updater.

Every hour

Runs Reload Extract Updates - fixes teammates add during the day are used in the next cycle.
